AIOps Multi Agent Platform v2

Bedrock AgentCore + 2-Tier Harness + Domain Gateway (awsops 130 MCP Tools)

Platform Design Principles

AIOps v2는 "Agent를 개발하는 것이 아니라, 검증된 부품으로 Domain Agent를 조립하는 Platform"이다. 아래 4가지 설계 원칙이 아키텍처 전체 의사결정의 근거가 된다.

01

Platform ≠ Agent

Control Plane과 Data Plane의 완전 분리

Platform Layer(ECS Fargate)는 Agent의 생명주기를 관리하는 Control Plane이고, Agent Runtime(Bedrock AgentCore)은 실제 추론과 도구 실행을 담당하는 Data Plane이다. 두 계층은 물리적으로 분리되어 있으며, boto3 invoke_agent_runtime()으로만 통신한다. 이 분리 덕분에 Platform 장애가 실행 중인 Agent에 영향을 주지 않고, Agent 수를 독립적으로 스케일링할 수 있다.

02

Tool 공유, Agent 독립

Agent는 추론하고, Tool은 실행한다 — 둘의 경계가 플랫폼의 핵심

Agent = 판단(Reasoning), Tool = 실행(Execution)으로 역할이 명확히 분리된다. Agent는 LLM으로 "무엇을 할지" 결정하고, Tool은 결정된 작업을 원자적으로 실행하는 stateless 함수다. 각 Agent는 Config의 gateways[]와 toolFilter로 자신의 Context Boundary에 맞는 Tool만 선택적으로 바인딩한다. Supervisor는 각 Agent의 Agent Card(capabilities, delegatesTo)를 읽어 사용자 의도에 맞는 Agent를 LLM으로 라우팅한다.

03

Agent = DDD Bounded Context

사용자가 정의한 Context Boundary가 Agent의 범위를 결정

Agent는 코드가 아니라 Config로 정의된다. Builder Agent와의 대화에서 사용자가 Context Boundary를 정의하면, Platform이 System Prompt + Gateway/Tool 바인딩 + Model 선택을 자동으로 조립한다. 이 세 가지가 Agent의 정체성이며, DDD의 Bounded Context 개념을 Agent 설계에 적용한 것이다.

04

Base Image + Config Injection

모든 Agent는 동일한 Base Image, 차이는 DynamoDB Config에서 주입

모든 Agent Runtime은 동일한 Docker Base Image(Strands SDK + Agent Harness)를 사용한다. Agent 간 차이는 오직 DynamoDB에 저장된 Config(System Prompt, Gateway 바인딩, Model, Harness 설정)에 의해 결정된다. 새 Agent를 만들 때 코드를 작성하지 않고, Config만 정의하면 Platform이 동일한 Base Image로 Runtime을 프로비저닝한다.
